# Lumora Desktop Runtime for Linux (Section 10A)

> Normative document of the Lumora Master Plan. Section numbers are stable IDs shared by all files and are not contiguous inside one file. Read `LUMORA_MASTER.md` first.

## 10A. Lumora Desktop Runtime for Linux

### 10A.1 What it is

A native Linux program that loads a `.lumora` package and renders it as the desktop wallpaper, using the same core, RHI (Vulkan), renderer, Lua VM and package format as Android. Plus a small control surface (a tray/control app and a CLI) to pick the scene, set per-scene settings (generated from `settings.json`), pick quality and frame cap, pause, and quit. Arabic/English with RTL applies to the control app (Section 13).

### 10A.2 Showing a wallpaper: the GNOME-first reality

Linux has no single wallpaper API. The earlier framing treated GNOME as one option among several and scheduled the deciding spike at the start of milestone ML (after the Android product is built). The four-reviewer pass showed that was backwards: the owner's confirmed desktop is GNOME on the newest Ubuntu, and since Ubuntu 26.04 LTS (GNOME 50, April 2026) and 26.10 (GNOME 51, October 2026) the Ubuntu desktop is **Wayland-only** - the X11 session is removed, and an Xwayland client cannot place its window below all other windows. The earlier "X11 desktop-type window" and "Xwayland-based window" paths therefore do not exist on the owner's machine. The spike is moved to M0-M1 (it needs no renderer; see Section 17) and GNOME-on-Wayland is the primary case:

- **GNOME on Wayland (primary, owner's machine):** no frames are handed to the extension. The Hanabi README shows the extension is installed per GNOME version, that the video is played by a **separate GTK4 renderer app** with app id `io.github.jeffshee.HanabiRenderer` (its Troubleshooting section tells users to exclude that app id from Blur My Shell), and that its `main` branch targets GNOME 50+ on Wayland only. Reviewers report that the extension moves that app's window actor to the bottom of the shell's stack (source not read, so this placement detail is **unverified** until the spike reads Hanabi's source and runs it). Another reviewer's claim that Hanabi renders inside gnome-shell is contradicted by the README and is not adopted. **Design for Lumora:** the renderer is the Lumora process presenting a Vulkan swapchain on its own Wayland `xdg_toplevel` window; the extension only places and manages that window (bottom of the stack, hidden from Alt-Tab, dock and window lists, ignoring input) and talks to the runtime over a control-only D-Bus interface (window app id, monitor, pause, coverage state, pointer position). No pixels cross processes. Problems this brings, each a spike gate: the toplevel can appear in Alt-Tab and the dock, can take focus, and other extensions (blur, transparency) can affect it. Hanabi is GPL-3.0; copying its placement code is subject to a license-compatibility check against Apache-2.0 (Section 14.1: GPL never), so v1 studies its approach and writes its own. Extensions declare supported shell versions; the realistic maintenance risk is mutter/window-actor internals more than the listed extension APIs (the GNOME 50 and 51 porting guides show few relevant changes, per the Linux reviewer, not re-fetched). GNOME support is labeled **experimental**.
- **Extension distribution and install:** extensions.gnome.org review guidelines say extensions must not ship binary executables or libraries and discourage spawning processes (reviewer-cited, not re-fetched), so the extension is JavaScript-only and the runtime is installed separately. Routes: (a) the `.deb` installs the extension to `/usr/share/gnome-shell/extensions/` (not reviewed by extensions.gnome.org; the user still enables it and, on Wayland, logs out and in the first time); (b) publish a thin client on extensions.gnome.org that talks to an already-running D-Bus service; (c) the AppImage cannot install a system extension, so the control app copies it to `~/.local/share/gnome-shell/extensions/` and tells the user to log out and in. First-run onboarding (enable extension, re-login) is added to the acceptance criteria and the Linux owner script. Route choice is open question OQ7.
- **Who starts whom:** the extension launches the renderer (Hanabi's model), so the runtime is not independently autostarted on GNOME; this survives shell restarts. A shell crash or restart kills extension state and can leave orphan renderers, so the control app detects and reaps them. The GNOME lock screen is its own shield, so the wallpaper is not shown there.
- **Mutter layer-shell:** reported by third-party projects as present-but-experimental since mutter 47, but not found in official GNOME documentation and not in stable upstream (only third-party mutter forks exist, per the Linux reviewer). Treated as non-existent; dropped as a fallback; one footnote only, no spike time.
- **KDE Plasma:** Plasma draws its own desktop, so a pure layer-shell background is not the path; the working projects use a Plasma wallpaper plugin (QML). KDE is **post-v1** (the owner has no KDE machine, 4.4); if added later it is a wallpaper plugin hosting or launching the native renderer.

- **Wayland, compositors with a background-layer protocol** (wlroots-based compositors): a background-layer surface. Secondary; best-effort.
- **X11:** a borderless window of the desktop window type, kept below all other windows, with input passed through to the desktop. Kept as a **secondary** path only, for X11 sessions on other desktops/flavors; irrelevant to GNOME 50+.

The spike produces `docs/linux-wallpaper-matrix.md` before any per-desktop promise is made, and the risk table (Section 18) no longer treats "honest unsupported-desktop message" as an acceptable GNOME outcome: GNOME is the owner's own machine, so failure there fails D27 on his hardware. The GNOME design direction (extension companion) is awaiting the owner's approval (open question OQ7); it is not an owner decision.

### 10A.3 Lifecycle and power policy (same hard rules as Android, adapted)

- Render only while visible: pause when the wallpaper is fully covered (maximized and opaque, not just fullscreen, where detectable; the extension pushes a per-monitor coverage boolean over D-Bus), when the screen is blanked or locked, and optionally when on battery (laptops). On GNOME/Wayland a client has no API for other apps' window state, so **coverage detection exists only inside the Shell extension**; without it the runtime falls back to Wayland frame callbacks (which stop when an occluded normal surface stops being drawn - verified in the spike, not guaranteed for layer/extension surfaces), plus logind session `Lock`/`Unlock` and `PrepareForSleep`, GNOME's `org.gnome.Mutter.IdleMonitor` (private interface, isolated behind an adapter), GNOME power-saver profile (`net.hadess.PowerProfiles`) and UPower for on-battery policy, plus a manual toggle and a timer-based policy, and the limitation is shown in the control app. Hard rule everywhere: pause on screen blank, lock, and suspend. A hidden or background toplevel may keep receiving frame callbacks from mutter, so "callbacks stop when occluded" is unproven for this case: it is a spike gate, with the extension pausing the renderer explicitly as the fallback.
- Frame cap: user-selected (30/60/refresh-rate/auto); refresh rate is queried per monitor. Idle target is measured with a methodology analogous to Section 16.3 on whatever hardware the owner provides; no battery figure is promised before measurement.
- Multi-monitor: one surface per monitor, per-monitor scene or span (decision for the owner, see the other open items in the master); HiDPI and fractional scaling honored. Hot-plug, suspend/resume and GPU reset recover without losing the scene.
- Thread model as Section 10.3 (render thread, logic thread, asset workers); the state machine is shared with Android where it fits.

### 10A.4 Input mapping (scene authors see capabilities, not platforms)

The Lua API exposes **capabilities** and the runtime reports which exist. Scenes degrade gracefully when one is missing; the editor warns per target platform (Section 11.2).

| Android input | Linux desktop equivalent |
|---|---|
| Touch / drag | Pointer position, clicks (only when wallpaper input is enabled; X11 can pass input through, Wayland layer surfaces can request pointer input but then cover desktop clicks, so default is global pointer position without capture where the compositor allows it; verified per desktop). On a hidden input-through toplevel a Wayland client gets no global pointer position, so the GNOME extension forwards it over the D-Bus control channel; pointer-reactive scenes are extension-dependent. Placing each per-monitor window is likewise the extension's job (clients cannot position their own windows). |
| Gyroscope / accelerometer / light | Not available on desktops (a laptop with sensors is not assumed). Scenes may use pointer position as an authoring substitute; the editor offers mock input |
| Screen on/off, lock/unlock | Session lock/unlock and idle/suspend via the login-session service (D-Bus), where the desktop provides them |
| Time, battery | Time; battery on laptops; AC state |
| Audio-reactive (mic / media session) | System audio monitor (PipeWire or PulseAudio), permission through the sound server, opt-in per scene; microphone on request only |
| Notifications | **Not supported on Linux in v1** (no portable listener API; would be a separate project) |
| Per-app foreground or window events | Not available to a Wayland client; window-coverage state exists only inside the GNOME Shell extension (10A.3). Otherwise not in v1 |

### 10A.5 Packaging and autostart (decided D28)

**Decided (D28):** x86_64 only, shipped as an **AppImage and a `.deb`**. Ubuntu 22.04 standard support ends in April 2027 (reviewer, standard five-year term; not confirmed on the Ubuntu page) and the owner runs 26.04 or newer, so: the `.deb` is built and tested on **26.04 and 26.10** (container matrix in CI) and declares its runtime dependencies (Vulkan loader, Mesa drivers, PipeWire/D-Bus client libs); the AppImage is built on the **oldest supported baseline** for glibc compatibility (24.04 once 22.04 drops out) with a FUSE3-capable runtime (the new static type2-runtime, named in CI), tested with FUSE removed and with `--appimage-extract-and-run`. The AppImage does not bundle `libvulkan` or Mesa (drivers come from the host; also tested on NVIDIA proprietary), cannot install the GNOME extension (see 10A.2), and the autostart entry path is rewritten on every launch because an AppImage path changes on update. Packaging smoke tests run in containers on clean 24.04, 26.04 and 26.10; GNOME-specific checks are in the nested-shell CI job or owner-side. `.rpm`, Flatpak and others are later and not promised. Autostart: a user-level entry set by the control app (toggle, off by default), no root and no system service (on GNOME the extension starts the renderer, 10A.2). Sandboxed formats (Flatpak/Snap) restrict window-layer and audio access and are not assumed to work.

### 10A.6 Security

The Section 15 model is unchanged: the same package validator, Lua sandbox and permission declarations apply. Linux adds: no scene may execute programs or read files outside its package; audio capture is opt-in and off by default; the runtime never opens network connections. **GNOME Shell extension security:** the extension companion is JavaScript running inside gnome-shell, so it is kept deliberately thin: it hosts placement and window-state signals only, never parses scene data, never executes scene code (scene Lua runs only in the sandboxed native process), and talks to the runtime over a versioned, minimal local IPC defined in `docs/security-model.md`.


### 10A.7 Spike success criteria and provenance rule

**What "success" means for the M0-M1 GNOME spike**, so it can be judged: a GPU-rendered Lumora toplevel (a) sits below all other windows, (b) is hidden from Alt-Tab and the dock, (c) passes input through to the desktop, (d) works per monitor, (e) pauses when covered, and (f) survives extension enable and disable. Agent-side evidence is a nested-shell run and source review; it is labeled unverified on real hardware until gate G7.

**Provenance rule for the GPL reference extension.** Hanabi is GPL-3.0 and this repository is Apache-2.0. To keep the extension defensible: record which GNOME and Mutter documents and APIs the placement code was written from, keep a short provenance note per function, and do not copy code, structure or comments from Hanabi. A second reviewer pass on that code before release is open question OQ10.
