# Milestones and effort (Section 17)

> Normative document of the Lumora Master Plan. Section numbers are stable IDs shared by all files and are not contiguous inside one file. Read `LUMORA_MASTER.md` first.

## 17. Milestones

Work proceeds in the order below; each milestone ends with a progress message to the owner (D23), and files/APKs are only delivered at the very end (D23) with the three owner test scripts (Section 16.2), unless the owner decides otherwise on CI-built test builds (open question OQ6). The repository and CI exist from M0 (D31). "Done" for a milestone means its exit criteria pass in CI or agent-side testing, labeled per Section 16.1. Gate numbering is **G1 to G7 everywhere**.

- **M0: Foundations and CI.** Repo skeleton, CMake superbuild, dependency pins, license, coding standards doc, example-scene format draft, the CI pipeline of Section 14.2 (Linux, Windows, Android build jobs, secrets policy, pinned runners), and the single entry-point test script that local runs and CI share. Also: the window layer is pinned (SDL3 default, GLFW fallback), Dear ImGui and DXC versions pinned, NDK chosen for 16 KB alignment, the first CI run answers whether KVM works for the emulator (with a recorded fallback if not), the WARP and software-Vulkan-on-Windows spike is started, and the GNOME spike starts. *Exit: CI is green on Linux and Windows and builds the Android app; the Windows editor empty-window smoke test passes on the Windows runner (CI-verified, no GPU) and the Vulkan init is checked via the software ICD if the spike allows; an API 29 emulator boots in CI and runs one instrumented test. The RHI hello triangle is not an M0 exit (the RHI is built in M1).*
- **M0-M1: GNOME wallpaper-method spike.** (a) Read Hanabi's source and run its extension on GNOME 50/51 in the nested-shell CI job; (b) prove a Lumora-style Vulkan toplevel can be placed at the bottom of the stack, hidden from Alt-Tab and the dock, input-through, per monitor, and survives enable/disable; (c) check the layer-protocol path headless; (d) produce `docs/linux-wallpaper-matrix.md`. **Agent-side output is source review and a nested-shell run, labeled unverified on real hardware.** Because the real mechanism can only be proven on the owner's GNOME, ML's design follows its result and **a fallback scope is defined now**: if the extension path fails or is not acceptable, the Linux runtime ships as a normal-window "wallpaper" mode with a documented limitation,; deferral to a later release is not a planned outcome, because D27 puts the Linux wallpaper runtime in v1: if the spike fails, work stops at the M0-M1 boundary and the owner is asked what to do. The spike failing degrades Linux scope and never blocks M10. Success criteria are in Section 10A.7. A short owner-side Linux session on his dual boot, early, is the cheapest way to settle this (open questions OQ6 and OQ7).
- **M1: RHI core.** Vulkan backend complete (swapchain, pipelines, buffers, textures, sync, validation-clean) + GLES 3.2 at feature parity for the required set; D3D12 backend compiled, linked and DXIL-compiled on Windows CI, with WARP-based device/clear/draw and golden tests if the spike works (labeled WARP software evidence; **never RX 570 evidence**). *Exit: Vulkan and GLES golden suites green in CI; D3D12 build/link/DXIL green on Windows CI; WARP result recorded (works or documented fallback); the Android emulator "hello triangle" through the same RHI.* G5 on the RX 570 stays the real-GPU confirmation.
- **M2: Runtime MVP.** WallpaperService hosting the core; simple scene at proper frame pacing; visibility/pause rules; fps overlay; the Section 10.6 checklist items (16 KB, manifest metadata, Direct Boot rule, flavors, AAB path), the engine in its own process, and the crash-loop breaker (Section 10.7). *Exit: on emulator, wallpaper runs, pauses when hidden, respects frame cap; CI emulator lanes API 29, 34, 36 pass.* **Checkpoint:** re-estimate the rest of the plan at the M2 boundary (owner-visible go/no-go on scope, D23-compatible progress message).
- **M3: Scene format + packer.** `scene.json`/manifest spec, packer CLI, checksums, loader, sample scenes, round-trip tests, signature-block rules (Section 15). *Exit: a scene built by hand as files, packed, loaded and rendered identically.*
- **M3S: Vertical slice.** One 2D parallax scene (layers, touch or offset parallax, one Lua script, one settings knob) authored as files, packed by the packer, loaded by the Android runtime on the emulator, and rendered as a golden image in CI. It pulls a minimal Lua binding forward from M5 and the 2D layer path from M4a. Physics, video, GPU particles and shadows stay behind it. 2D parallax is the most common live-wallpaper type, so this is also the first useful product. *Exit: the golden image matches in CI on the emulator lane, and the same scene runs on the Linux software renderer.*
- **M4: Renderer features.** M4a (glTF static + skeletal, PBR + IBL, 2D layers, text via the Section 13 stack) and M4b (shadows, post-FX, particles, video textures); per-tier pass budget enforced from M4b. *Exit: feature demo scenes pass golden tests on Vulkan and GLES; D3D12 coverage is build/link/DXIL, plus WARP goldens if available.* **Checkpoint:** second re-estimate at the M4 boundary.
- **M5: Scripting.** Lua VM embedded, allowlist sandbox, native stdlib limits, cooperative cancellation plus process-level recovery (Section 9.1; the VM-in-own-process option is measured here), shader static limits and adversarial shaders in the fuzz corpus (Section 15.1), engine API v1 including the 9.4 additions, reduced motion (9.5), event dispatch, watchdog. *Exit: sample interactive scenes work on emulator; the full escape suite passes.*
- **M6: Interaction layer (non-audio).** All Section 9.3 sources except audio analysis wired on Android with permission flows; `settings.json` to settings screen; quality/frame-rate controls; `play` and `full` flavors. *Exit: interaction demo scene reacts to every non-audio input on emulator (mocked sensors where needed).* Audio-reactive inputs move to M8 (the analysis core lands there).
- **MT: Lumora text engine.** The text engine of Section 13 and the Dear ImGui wrapper API, with the Arabic IME and Wayland typing spikes. *Exit: shaped, bidi-correct text in a test harness covering mixed strings, caret, selection and word wrap; reduced scope if the owner chose option (b).*
- **M7a: Editor MVP.** Docking shell (single OS window), hierarchy/inspector/viewport, asset import, material/shader editors, live preview with device profiles, export pipeline (shaders to 3 targets, textures to KTX2, pack), undo/redo, autosave. The UX and RTL prototypes (11.3, 13) gate it. The authoring-experience work item (Section 11.5) is due by the end of M7a. *Exit: non-physics, non-audio sample scenes authored in the editor end to end and run on the emulator.*
- **M8: Physics & audio.** Jolt integration (with the input sanitizing of Section 12) + editor physics panel groundwork; Oboe playback; libogg/opusfile/vorbisfile decode; audio-reactive analysis core and its Android wiring; global mute. *Exit: physics + audio demo scene passes tests, including the audio-reactive inputs deferred from M6.* M8 comes **before** M7b because the physics panel, particle collision and the full sample set depend on it.
- **M7b: Editor full.** Timeline and curve widget, particle editor, physics panel, interaction binder, settings designer, send-to-phone. Cut order if the estimate is exceeded: send-to-phone, settings designer, interaction binder (all have manual workarounds); core authoring and export never slip. *Exit: the full sample scene set, including physics and audio scenes, is authored in the editor end to end and runs on the emulator.*
- **M9: Android app polish.** Library UI, RTL Arabic + bidi pass, onboarding (restricted-settings step), permissions center, diagnostics screen, lock-screen flow, performance gates within software-rendering limits. *Exit: every app screen passes screenshot review in both languages; the permissions center grants/denies/revokes each capability live; diagnostics export is complete.*
- **ML: Linux editor and Linux desktop runtime.** Steps: (1) consume `docs/linux-wallpaper-matrix.md` and implement the chosen GNOME design (extension launches the Lumora renderer toplevel, 10A.2); (2) Linux platform layer and window layer; (3) Linux editor build running the M7 feature set on Vulkan; (4) desktop runtime: per-monitor windows, pointer/session/audio inputs, power policy, control app and CLI, extension install onboarding; (5) desktop texture/export profile (BC7) and capability warnings; (6) packaging on the 26.04/26.10 matrix. The Linux editor build follows M0 and M7a continuously in CI; the runtime steps run after M6 and M9. *Exit: CI-verified and agent-verified (software renderer) on the Linux matrix; real-desktop behavior pending owner-side validation (G7).*
- **M10: Release prep and owner gates.** Release signing per `docs/release-and-signing.md` (keystore as a protected-environment secret, version-code policy, Play App Signing decision), signed APK and AAB, Play prep (Data safety form, privacy policy, permission declarations), Windows packaging route per open question OQ5, sample-scene pack, README (Arabic + English), THIRD_PARTY_NOTICES and dependency manifest complete, the three owner test scripts, final full sweep, delivery. Diagnostics/log export ships at M9. The M10 checklist also revokes the repository access token and any other credential created for the project, and confirms secret scanning stayed on. **Owner-verification gates (run here per D23):** G1 first render on the physical Realme 6; G2 a Windows-exported package loaded on the Realme 6; G3 surface/visibility/lock-screen lifecycle on the real OEM firmware (records what the lock screen does, 10.3); G4 thermal and battery baseline; G5 D3D12 and Vulkan real-GPU validation on the RX 570 (the only claim of RX 570 evidence anywhere in the plan; it confirms, and no longer is the first evidence); G6 cross-backend capability and fallback validation; G7 Linux real-session validation on the owner's dual boot, owner-hardware-verified. Each gate report records build/commit, device and OS, GPU and driver, backend, scene, expected vs actual, logs and limitations. *Exit: CI builds the signed release artifacts green; every Section 16 artifact set is complete; G1-G7 pass or their failures are fixed or documented.*

**Integration and regression reserve:** each milestone from M4 onward reserves explicit time for cross-backend integration, Android compatibility fixes, performance, security testing and regression passes; Section 17.1 quantifies it.

Milestones are sequential in listing but overlap where safe (docs and tests are continuous; M7a's export pipeline starts when M3 lands; the Linux editor build tracks M7 in CI).

### 17.1 Rough effort picture

One developer-equivalent, serial execution. Judgment estimates, not promises; the first calibration comes from M0-M2, and re-estimates happen at the M2 and M4 boundaries.

| Item | Rough estimate (weeks) |
|---|---:|
| Specs and docs (continuous, 12+ documents) | 3-5 |
| M0 Foundations + CI | 2-4 |
| M0-M1 GNOME spike (source review + nested shell) | 1-2 |
| M1 RHI core (incl. WARP D3D12 on CI) | 5-9 |
| M2 Runtime MVP (16 KB, API lanes, flavors, process split, crash-loop breaker) | 4-6 |
| M3 Format + packer | 2-3 |
| M3S Vertical slice (2D parallax scene, end to end in CI) | 2-4 |
| M4 Renderer (a+b) | 6-10 |
| M5 Scripting (sandbox hardening, native stdlib limits, shader static limits, process-level recovery) | 5-8 |
| M6 Interaction (non-audio) | 3-5 |
| MT Lumora text engine | 4-8 |
| M7a Editor MVP | 7-11 |
| M8 Physics & audio | 3-5 |
| M7b Editor full (incl. custom timeline/curve widget) | 5-9 |
| M9 App polish | 3-4 |
| ML Linux editor + runtime (high risk, revised after spike) | 6-10 |
| Test infrastructure beyond M0 (fuzz, goldens, packaging) | 2-4 |
| Sample and benchmark content authored in the editor | 2-4 |
| Authoring experience (manual, tutorial, templates, LuaLS stubs, script console, live reload) | 2-3 |
| CI iteration latency reserve (push-and-wait loops, artifact-based debugging) | 3-5 |
| Integration and regression reserve (M4 onward) | 4-6 |
| M10 + gates G1-G7 (owner availability assumed) | 6-10 |
| **Total (serial)** | **80-135** |

That is roughly 18-31 months of focused work (weeks divided by 4.33). The rows added since the previous plan version (vertical slice, authoring experience, CI latency reserve, and larger M2 and M5 rows) are judgment estimates like the rest.

The pre-defined response when an estimate is exceeded: report it at the milestone boundary, apply the M7b cut order where applicable, and re-estimate the rest. Scope cuts beyond the cut order are the owner's call, never silent. M10 assumes the owner can run a script and report within a few days; his availability is not budgeted and is a risk row (Section 18).
