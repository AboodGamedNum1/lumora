# zeckendorf: Fibonacci numbers and Zeckendorf representations

Code: `core/zeckendorf/zeckendorf.cpp` (contract in `core/zeckendorf/zeckendorf.h`). Tests: `tests/zeckendorf/zeckendorf_tests.cpp`. Reference: `tools/zeckendorf_ref.py`. Evidence label: unit tests only.

## Rule

F(0) = 0, F(1) = 1, F(k) = F(k - 1) + F(k - 2).

- `fib(k)` gives F(k) for k from 0 to 93; k above 93 is TooLarge.
- `zeckendorf(n)` writes the indices of the Zeckendorf form of n, largest first, to a caller buffer, and the number of terms to `*count`. Every index is from 2 to 93, strictly decreasing, no two adjacent. n = 0 gives no terms.
- `zeckendorf_value(idx, count)` is the inverse: the sum of F(idx[i]). The list must be valid (each index from 2 to 93, a difference of at least 2 between neighbours, an empty list is valid and gives 0).
- Check order. `fib`: a null out pointer is NullArgument, then k above 93 is TooLarge. `zeckendorf`: a null `idx` or null `count` is NullArgument (also for n = 0 and for cap 0); then a `cap` below the term count is BufferTooSmall. `zeckendorf_value`: a null `out`, or a null `idx` with count above 0, is NullArgument (a null `idx` with count 0 is valid and gives 0); then the WHOLE list is checked (BadArgument); then a sum above 2^64 - 1 is TooLarge. Nothing is written on a failure, BufferTooSmall included (the buffer and `*count` are untouched). n = 0 with cap 0 and a non-null `idx` is Ok with count 0.
- Integer only: no floating point, no 128-bit type, no builtin, no heap, no recursion, no mutable static, no array, no table of Fibonacci numbers. Every call takes O(93) steps.

## Method

A pair (hi, lo) = (F(k), F(k - 1)) walks up one step to (hi + lo, hi) and down one step to (lo, hi - lo). The walk up never goes past k = 93, so F(94) is never formed: the climb in `zeckendorf` stops at k = 93, and the climb in `zeckendorf_value` stops at the first (largest) index, which is at most 93 after the list check.

- `fib(k)`: from (a, b) = (F(0), F(1)) it steps k - 1 times, the last step giving F(k).
- `zeckendorf(n)`: climb to the largest k <= 93 with F(k) <= n, then repeat: walk down while F(k) is above the remainder, take the term k, subtract F(k) from the remainder. Two passes: the first only counts, the second writes, so a too-small `cap` is detected before anything is written.
- `zeckendorf_value`: the first loop checks every element (index below 2 or above 93, or a difference below 2 to the element before) and stops at the first violation, so a count far above 92 never reads past the first bad element (a valid list cannot have more than 46 elements, so a list longer than 46 has a violation at element 47 at the latest). Then it climbs to the first index, and for each element walks down to its index and adds F(index) after the test `F > 2^64 - 1 - sum` (exact: the sum fits iff `F <= 2^64 - 1 - sum`).

## Proofs

**Lemma (sum of a valid list).** A valid list whose largest index is k sums to at most F(k + 1) - 1. Induction on the length: a single term F(k) <= F(k + 1) - 1 for k >= 2. Otherwise the sum is F(k) plus a valid list with largest index at most k - 2, which is at most F(k - 1) - 1 by the induction (F is non-decreasing), and F(k) + F(k - 1) - 1 = F(k + 1) - 1. (For an empty rest the sum is F(k) <= F(k + 1) - 1.)

**Existence and uniqueness (Zeckendorf).** Existence by the greedy rule below. Uniqueness: if a valid list for n has largest index k, then F(k) <= n <= F(k + 1) - 1 (the term and the lemma), so k is the largest index with F(k) <= n: it is forced. The rest is a valid list for n - F(k) with indices at most k - 2, and the same argument applies to it. So the list is unique and equal to the greedy one. Indices start at 2 because F(1) = F(2) = 1 would make the list ambiguous.

**Greedy correctness.** Take the largest k >= 2 with F(k) <= n. Then n < F(k + 1), so the remainder n - F(k) < F(k + 1) - F(k) = F(k - 1). Every F(j) with j >= k - 1 is at least F(k - 1) (non-decreasing for j >= 2), so the next index is at most k - 2: the list is strictly decreasing with no two adjacent, and ends because the remainder falls at every step (F(k) >= 1). The code does exactly this: after a term it walks down while F(k) is above the remainder, which takes at least two steps.

**The pair walk.** From (F(k), F(k - 1)): up gives (F(k) + F(k - 1), F(k)) = (F(k + 1), F(k)); down gives (F(k - 1), F(k) - F(k - 1)) = (F(k - 1), F(k - 2)). Starting at k = 2 with (1, 1).

**F(93) fits and F(94) does not.** F(93) = 12200160415121876738 <= 2^64 - 1 = 18446744073709551615, and F(94) = F(93) + F(92) = 19740274219868223167 is 1293530146158671552 above 2^64 - 1 (2^64 - 1 - F(93) = 6246583658587674877 is below F(92) = 7540113804746346429). So kMaxIndex = 93 is exact, and every n <= 2^64 - 1 has all its indices at most 93 (a largest index of 94 would need n >= F(94)). The values were computed in the Python reference with unbounded integers, and the test checks F(93) + F(92) > 2^64 - 1 without forming it.

**46 terms, and why not 47.** The indices lie in 2..93, which is 92 values, grouped in the 46 pairs (2, 3), (4, 5), ..., (92, 93). Two indices of one pair are adjacent, so a valid list takes at most one from each pair: at most 46 terms. Equivalently 47 terms with gaps of at least 2 need a largest index of at least 2 + 2 * 46 = 94. This is a bound on the list, not on the value, and it needs no u64 argument. It is reached: the even list 92, 90, ..., 2 sums F(93) - 1 = 12200160415121876737 (below), which is a u64, so `kMaxTerms` = 46 is exact for u64 as the header says. The test also feeds 47-element lists (94, 92, ..., 2 and 93, 91, ..., 1): BadArgument.

**Even and odd lists.** F(2) + F(4) + ... + F(2m) = F(2m + 1) - 1 and F(3) + F(5) + ... + F(2m + 1) = F(2m + 2) - 1 (induction: add F(2m + 2) to F(2m + 1) - 1 to get F(2m + 3) - 1, and the same for the odd list from F(3) = 2 = F(4) - 1). So F(k) - 1 has floor((k - 1) / 2) terms, every other index from k - 1 down: F(93) - 1 has 46 (the evens 92..2).

**The largest valid index sum, F(94) - 1.** By the lemma the largest sum of a valid list is at most F(94) - 1 (largest index 93), and the odd list 93, 91, ..., 3 (46 terms) reaches it: its sum is F(94) - 1 = 19740274219868223166, which is 1293530146158671551 above 2^64 - 1. This is not the value of any u64 n; it is the largest value any valid index list can have, and it shows that TooLarge is reachable from a valid list (for example 93, 91, 89 = 18640186441502121236). Valid lists that sum to exactly 2^64 - 1 (26 terms: 93 91 88 86 82 76 74 70 66 63 59 56 47 44 40 37 33 31 29 25 19 17 13 11 5 3, Ok) and to exactly 2^64 (25 terms: the same list with 5 and 3 replaced by 6, TooLarge; -5 - 2 + 8 = +1) are in the tests, with every single-term change around them.

**BadArgument before TooLarge.** The list is checked in full before any sum, so a prefix that already overflows does not hide a later bad index: 93, 91, 89, 89 (and 93, 91, 89 followed by 94, 88 or 1) are BadArgument although 93, 91, 89 alone is TooLarge.

## Tests

Expected values come from the header's examples, from a test-only Fibonacci list used by a different method (the library walks a pair; the test subtracts from the list), from the definition (a list is valid and its sum is n; an Ok list of a sum is the Zeckendorf list of that sum), from closed forms, and from FNV-1a 64-bit digests made by `tools/zeckendorf_ref.py` (Python standard library only; bigint Fibonacci list, bisect and subtraction; the sum of a list is exact, so TooLarge is "sum above 2^64 - 1"). Every call passes its result cells between guard words or buffers of exactly the needed size (an overread or overwrite is an ASan error).

Extents and local runtimes (gcc 11.4.0, `-O1`, ASan + UBSan, one core, base 6c6813d; the whole binary has 24 cases and 143 assertions and runs about 2.4 s; the longest case is 0.47 s; none asserts time; declaration order):
- `header examples`, `failure cases`, `long counts`, `fib: every k`: each under 0.01 s. The failure case covers the null matrix (also n = 0 and cap 0), BufferTooSmall with the buffer and `*count` untouched, n = 0 with cap 0, and the order of every check. `long counts` has lists of exactly 47 bytes with counts 47..255 and 1000000, bad first elements with count 4000000000, the 47-element lists above and every prefix of the odd list. `fib` has every k = 0..93 (digest and the identity F(k) = F(k - 1) + F(k - 2)) and k = 94, 95, 100, 255, 65536 and 4294967295 (TooLarge, nothing written).
- `chunk 0` to `chunk 3`: exhaustive, every n = 0..2^22 (2^20 each, the last includes 2^22): the indices against the test list, the definition (`zeckendorf_value` gives n back), the terms at most 46, nothing written past the terms, a `cap` one below the term count (BufferTooSmall, untouched), digest. 0.43 to 0.47 s each.
- `structured`: F(k) - 1, F(k), F(k) + 1 for every k = 2..93, 2^k - 1, 2^k, 2^k + 1 for k = 0..63, 2^64 - 1 and 2^64 - 2 (470 values, digest, exact-size buffer), plus the term count floor((k - 1) / 2) and the indices of F(k) - 1.
- `the all-even and all-odd lists`: every even list 2m..2 (sum F(2m + 1) - 1) and every odd list 2m + 1..3 (sum F(2m + 2) - 1, TooLarge for the full list 93..3).
- `the 46-term maximum, caps`: values with 0, 1, 25, 26 and 46 terms (0, 1, 2^64 - 3, 2^64 - 1, F(93) - 1) and also F(93) - 2 and 4, for caps 0, 1, 25, 26, 45, 46 and 255, in exact-size buffers.
- `arithmetic lists`: every list a, a - d, a - 2d, ... for d = 2..6, every start 2..93 and every length (6368 lists, digest).

The verdict of every list comes from the oracle (the deletion of a middle term can leave a valid list, so not every list is BadArgument); the call must agree with it, with the guard words intact, and the digest must match. 0.015 s.
- `around 2^64 - 1 and 2^64`: 10035 lists: every single-term change (every index 0..95 at every position), every deletion and every insertion (every index 0..95 at every position) of the lists of 2^64 - 1 and 2^64, digest. 0.006 s.

## Mutation testing

149 source mutants of `core/zeckendorf/zeckendorf.cpp` (script outside the repository), built with ASan + UBSan against the final tests (md5 7aabb7de189edf4585dc4a7023d3aa4d, not edited after the run), abort after the first failure, declaration order (`--order decl`), the whole suite for every mutant. Mutated: in the pass `expand` the start values, the climb test and bound, the step, the loop test, the descent test and step, the write and the term count, the remainder update, the return and the integer widths; in `fib` the null and range checks and their order and return codes, the start, loop bounds, the step and the result; in `zeckendorf` the null checks and their order, the n = 0 case, the `cap` comparison and its return code, the writes and the count; in `zeckendorf_value` the null checks, every list check (range, adjacency, first element, return codes, order against the sum), the climb, the descent, the overflow test (four variants), the sum, the output and the widths.

- 116 killed by a failed assertion, and 8 killed by an abnormal end (a sanitizer abort or a crash: a null pointer written or read once a null check is removed).
- 11 step-limited, not counted as kills, non-termination not proven: the climb or descent mutants (`ex_up_nok`, `ex_up_gt`, `ex_up_or`, `ex_up_swap`, `ex_up_sub`, `ex_down_ge`, `ex_down_lo`, `ex_down_add`, `ex_down_swap`, `ex_hi32`, `ex_t32`). Probed on the final file: each was rebuilt with a counter on every loop of `expand` that aborts when a loop (which must stop within 93 trips, 46 for the outer loop) has run 200000 trips, and with a repeat-state check from trip 4096 on. All eleven aborted at the limit in the first case that reaches them (state repeats were not seen: the wrapped sums and counters keep changing, so the evidence is the step limit, not a cycle; this shows a limit was hit, it does not prove a hang).
- 10 survivors, each equivalent:
  - `ex_up_hi` (climb test `hi <= n` instead of `hi + lo <= n`): the climb stops one index too high, and the descent loop, which runs while F(k) is above the remainder, brings it back before the first term, so the output is the same.
  - `ex_rem_all` (outer loop also stops at 46 terms) and `ex_terms_2` (the term counter adds 1 and one more when it is above 100): no n has more than 46 terms (the 46-term bound), so neither ever acts.
  - `ex_rem_loopback` (one extra step down after each term): after a term the remainder is below F(k - 1), so the loop would step down at least once anyway and the extra step is the first of those; the test `k > 3` only keeps the index from leaving the range.
  - `zk_n0_rm` (no n = 0 special case) and `zk_write_n0` (also write for n = 0): the pass returns 0 terms and writes nothing for n = 0.
  - `zv_up_le` (the climb goes one index above the first index): at the first index 93 it forms F(94) modulo 2^64, and the step down computes F(94) - F(93) modulo 2^64 = F(92) exactly (unsigned arithmetic wraps and is defined), so the pair is right again before the first addition; the real source avoids forming it.
  - `zv_ov_wrap` (`sum + hi < sum`): the usual wrap test, equal to `hi > 2^64 - 1 - sum` for unsigned values.
  - `zv_k_u8` (index counter as u8): k is at most 93.
  - `zv_early` (a dead branch `sum > 0 && sum < 0` added): it is never true.
- 4 cost mutants (the values are right, only the time grows; kept apart from kills and equivalent survivors; no test can detect them because the repository forbids timing assertions). Observed, whole suite (about 2.4 s for the source): `cm_ex_climb` (the pass climbs again from F(2) after every term) about 2.9 s, chunk 0 0.47 s; `cm_zv_scratch` (the value walk climbs from F(2) again for every element) about 2.7 s, chunk 0 0.45 s; `zk_cm_twice` (the count pass run twice before writing) about 2.6 s, chunk 0 0.46 s; `cm_zv_validate_twice` (the validity loop repeated 200 times after the real check) about 8.3 s, chunk 0 1.5 s. A repeat count of 20000 for the last one ran past the 40 s limit of the mutation run and is not counted as a kill.
