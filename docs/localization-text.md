# Localization and the text engine (Section 13)

> Normative document of the Lumora Master Plan. Section numbers are stable IDs shared by all files and are not contiguous inside one file. Read `LUMORA_MASTER.md` first.

## 13. Localization (D20)

- All user-facing strings in both apps live in string tables (Android resources; a simple key-value table in the editor). Arabic and English ship in v1.
- RTL: Compose handles app RTL automatically when Arabic is active; the editor's ImGui layout needs explicit mirrored docking (two generated layouts, Section 11.3), budgeted as real work, not an afterthought, and verified with screenshots.
- In-scene text rendering uses the same text engine (HarfBuzz shaping, bidi, FreeType) for correct Arabic shaping.
- **The Lumora text engine (milestone MT) replaces "HarfBuzz plus glyph ranges".** Reviewer finding, with upstream evidence the reviewer cited (Dear ImGui issues 4227 and 6536; not re-fetched here): Dear ImGui has no shaping or bidi, and the one working community implementation rewrote much of its text rendering. Shaped Arabic glyphs have no codepoints, so glyph ranges and merge mode do not work. The plan of record: a standalone text engine (HarfBuzz for shaping, SheenBidi or FriBidi for the Unicode Bidirectional Algorithm, FreeType for rasterization) with a shaped-run cache, a glyph-ID atlas, visual-order caret movement and multi-rectangle selection, bidi word wrap, and a small Dear ImGui wrapper API (`LText`, `LInputText`, `LTreeNode`) used in InputText, tables, tree nodes, tab titles, tooltips and menus, plus a pinned patch policy for `imgui_draw` and `imgui_widgets`. Budget 4-8 weeks on its own (a judgment estimate), before M7a. **Owner choice (open question OQ1):** this full engine, or a reduced scope with shaped read-only Arabic labels in the editor and editable Arabic only in scene-text fields.
- **Arabic-capable font is a real dependency:** a licensed Arabic font (Noto Naskh Arabic or Cairo, both OFL) is bundled in the editor, the runtime and in-scene text, with the license recorded in the manifest and THIRD_PARTY_NOTICES. With the text engine, glyphs are addressed by glyph ID, so no custom glyph ranges are used.
- **Bidirectional text:** HarfBuzz shapes glyphs but does not implement the Unicode Bidirectional Algorithm. The text stack is HarfBuzz (shaping) + SheenBidi (Apache-2.0) for the Unicode Bidirectional Algorithm, with ICU as the fallback if SheenBidi proves insufficient so mixed Arabic/English strings, numbers, and punctuation lay out correctly, in the editor and in scenes. Editable fields additionally need bidi caret movement and selection, clipboard behavior, IME handling, Arabic-aware search/filter, directional-icon mirroring rules, and font fallback for missing glyphs. Verified with screenshot tests of mixed-direction strings; the full spec is `docs/rtl-support.md` (M7/M9).
- **Early RTL prototype:** at the start of M7a, on top of the finished text engine and alongside the editor UX prototype, an RTL prototype validates the real editor controls - not a rendering demo - covering mixed Arabic/English strings, numbers and punctuation, caret and selection, IME composition, clipboard, numeric fields, menus, tree views, tables, docking, keyboard navigation, and focus order. The code editor component has no bidi support upstream and is left-to-right only in v1 (11.3), so it is not on the RTL checklist. Findings fix the text stack before feature build-out continues.
