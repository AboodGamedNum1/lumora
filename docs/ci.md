### 14.2 Repository and CI design

The repository and GitHub Actions exist from M0. Design, from the build/CI, Windows and security reviews (hosted-runner facts were checked against the runner-images README: `windows-2025`, `windows-2025-vs2026`, `windows-2022`, `ubuntu-24.04`, `ubuntu-26.04` and arm variants exist, and `windows-latest` currently maps to the Windows Server 2025 images; the Ubuntu 22.04 retirement dates below are the reviewer's, unverified):

- **Pinned labels.** Never `-latest`. `windows-2025` or `windows-2025-vs2026` (chosen at M0), `ubuntu-24.04` and `ubuntu-26.04`. Ubuntu 22.04 runners are being retired per the reviewer (deprecation from 2026-09-17, retirement 2027-04-17, unverified), so 22.04 targets build inside `container: ubuntu:22.04` images if ever needed. lavapipe/Mesa is built from a pinned source into a cached toolchain image pushed to GHCR, not taken from the runner's distro.
- **One entry point.** The local test script, ctest and CI all call the same script, so they cannot diverge.
- **Jobs.** `ci.yml` on pull request and push: Linux build + ctest + lavapipe goldens + ASan/UBSan + a short fuzz smoke; Windows build + DXC/DXIL + WARP smoke + editor launch smoke + zip artifact; Android Gradle arm64 release build + ABI inspection + 16 KB alignment check + API 29 emulator job. `nightly.yml`: full emulator matrix (API 29, 34, 36), long fuzz with corpus kept as an artifact or cache, TSan, double-export determinism (rebuild on the same image and compare hashes of inputs and tool versions), nested GNOME Shell job. `release.yml`: on a protected tag only, with a protected environment and required reviewers, signing and artifacts. `bless-goldens.yml`: manual, opens a pull request with updated baselines.
- **Golden images.** Metric and tolerance are documented per scene (per-channel delta or SSIM, not exact match); separate baselines for lavapipe, SwiftShader, ANGLE and WARP; baselines live on an orphan branch or release assets (Git LFS has quotas); diff images upload as artifacts on failure; the CPU features of the runner are logged to catch JIT drift.
- **Android emulator.** `reactivecircus/android-emulator-runner` pinned by commit SHA, KVM on Linux runners (GitHub changelog 2024-04-02, cited by the reviewer), AVD snapshot cached, `timeout-minutes`, at most one retry on emulator jobs only, logcat artifact on failure. Emulator graphics are software, so they are never driver evidence. KVM on `ubuntu-24.04-arm` is unverified.
- **Caching.** The per-repository cache is 10 GB by default with 7-day eviction (reviewer, docs link not re-fetched), runner disk is small: ccache/sccache, a prebuilt toolchain image, vcpkg binary caching, Gradle caching, free disk space before NDK jobs, and a cache budget table in `docs/ci.md`.
- **Visibility and cost.** Public repositories get free standard runners; private ones spend a limited minute budget with higher Windows cost (exact numbers unverified). Proposal: public (open question OQ4). If private: path filters, `concurrency` with `cancel-in-progress`, heavy jobs nightly only.
- **Secrets and supply chain.** The default `GITHUB_TOKEN` is read-only (`permissions: contents: read` at the top of every workflow). Third-party actions are pinned to full commit SHAs and updated by Dependabot. No `pull_request_target` or `workflow_run` with untrusted pull-request code, and fork pull requests get no secrets. CODEOWNERS and branch protection require green CI. No key, keystore or certificate is ever committed. The Android release keystore and any Windows certificate live only as GitHub environment secrets in a protected environment, available to tags on `main`; debug keystore for ordinary CI. The repository token the owner provides arrives only through the vault; it is never written to a plan, file, workflow, log or message.
- **Quality gates.** License scan (GPL and AGPL blocklist per 14.1), dependency review and Dependabot, CodeQL, an SBOM, artifact attestation for releases, short artifact retention for APK, AppImage, MSI and golden diffs (private repos bill artifact storage). Required checks versus nightly are listed in `docs/ci.md`; flaky tests go to a quarantine list; benchmark jobs report CPU-side micro-benchmark trends only, never frame-time pass/fail (CI cannot measure battery, thermal, GPU time or real frame pacing).
- **Fast required checks versus slow nightly checks.** Required checks target under about 10 minutes (a target, not a measurement): build, unit tests, lint, and the documentation consistency check (`tools/check_docs.py`). Windows, emulator, long fuzz and GNOME jobs run nightly or on tags unless the change touches them. The split is written in `docs/ci.md`.
- **Failures must be debuggable without a rerun.** Every failing job uploads what a model needs: logs, diff images, crash dumps, logcat and the exact toolchain versions. The local container uses the same pinned image as the Linux CI job. CI latency is budgeted as its own row in the effort table (Section 17.1). The way the executor reads run status and logs through the GitHub API, and which token scopes that needs, is pinned at M0 (not verified here).
- **Flavor lanes (proposal).** `full` runs on every emulator lane (API 29, 34, 36). `play` runs on API 29 and API 36 only, to keep CI cost predictable.
- **Continuity checks.** `docs/PROJECT_STATE.md` is committed from M0 and updated at the end of every session; an ADR log (`docs/adr/`) records non-obvious decisions. CI fails if the `last_completed_milestone` field in `PROJECT_STATE.md` differs from the newest `m*-done` git tag.
- **How credentials reach the executor.** The repository access token (D31) reaches the executing session only through the platform's secure vault route. It is never pasted into chat, issues, commits, workflow files or logs. A session that cannot receive it through that route stops and asks the owner for a vault link; it does not accept the token in plain chat. The token is scoped to one repository, given an expiry when it is created, and revoked at project end (M10 checklist).
- **Secret scanning.** GitHub secret scanning and push protection are enabled on the repository (an owner action in repository settings), and CI runs its own secret scan on every push.
- **Optional extras.** Windows ARM and Linux ARM runners exist; they are not required.
